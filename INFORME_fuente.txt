1. Resumen ejecutivo

Prototipo de MLOps para predecir falla de equipos a 30 días: 2,400 registros, siete entradas, 647 positivos (27.0%), cero vacíos; 480 casos de prueba. Se compararon cinco variantes y se eligió E2 por mayor F1 entre las que superaron recall 0,50.

En prueba: recall 73.1%, precisión 44.6%, exactitud 68.1%; detecta 95 de 130 fallas con 118 falsas alarmas (IC95 recall [64.9%, 80.0%]). Meta propuesta: recall ≥70% y reducir en seis meses 25% las paradas no planificadas y 10% el costo correctivo.

Evidencias de ejecución: la validación rechaza datos corruptos; 15 pruebas en verde (mutación detectada); API 200/422; puerta forzada a 1,01 rechazada; GitHub Actions en verde y rojo; contenedor Docker construido y verificado; deriva detectada solo en temperatura.

<b>Recomendación a la junta:</b> autorizar la preparación de datos y un piloto en modo sombra; medir alertas, capacidad de inspección y resultados a 30 días antes de decidir uso operativo.

4. Proceso MLOps y métricas

4.1 Datos y validación

2.400 filas × 8 columnas, 647 fallas (27,0%), 0% vacíos, semilla 20261019; etiqueta por probabilidad logística (uso, temperatura, días sin mantenimiento, incidentes) más ruido. La validación exige columnas, finitud, rangos, enteros y objetivo binario; detiene el entrenamiento con ValueError (probado con un uso semanal negativo). Partición estratificada 1.440/480/480; escalado dentro del Pipeline solo con entrenamiento; prueba consultada una vez.

4.2 Experimentos y selección

La puerta de recall 0,50 se fijó tras el modelo base (0,24); el umbral de clasificación (0,50) es distinto del de aceptación.

4.3 Resultado final

Prueba reservada (480): exactitud 0.681, precisión 0.446, recall 0.731, F1 0.554; matriz VP=95, FN=35, FP=118, VN=232; 213 alertas. IC95 Wilson del recall [0.649, 0.800]. Costo esperado = costo_FN×FN + costo_FP×FP; el piloto fija esos costos y ajusta el umbral. Ver figuras A1 y A2.

4.4 Puerta, servicio, pruebas, CI y monitoreo

Puerta de calidad: si no cumple recall termina con código 1 y no guarda (probado con 1,01, campeón intacto). API FastAPI reutiliza el mismo Pipeline (200/422). 15 pruebas en verde (una mutación hizo fallar la esperada). GitHub Actions en verde y rojo; Docker construido y verificado.

Monitoreo de deriva (KS + Holm, α=0,01, D≥0,10) sobre 800 casos: alerta solo en temperatura_promedio (D=0.46); el control no alerta. Reentrenar por: deriva sostenida, recall <0,50 en cohortes maduras, o cada 90 días; cada candidato repite la puerta.
