1. Resumen ejecutivo

<b>Comercial Andina S.A.S. - Línea B: Operación</b><br/>Taller integrador Unidad 3. Informe preliminar. 19 de octubre de 2026.

La empresa ficticia tiene seis tiendas, 320 empleados y un equipo de TI de cuatro personas ocupado en soporte. Sus registros fragmentados y decisiones manuales limitan el uso sostenible de analítica [1]. Se propone priorizar inspecciones de equipos con un clasificador de falla a 30 días, sujeto a revisión humana y disponibilidad de mantenimiento.

Se ejecutó un prototipo con 2,400 registros sintéticos, siete entradas, 647 positivos (27.0%) y cero vacíos. Se reservaron 480 casos para prueba final. Se compararon cinco variantes en validación y se seleccionó E2 por mayor F1 entre las que alcanzaron recall de 0,50. La puerta es didáctica y no certifica seguridad industrial.

En prueba final, el modelo obtuvo recall 73.1%, precisión 44.6% y exactitud 68.1%. Detectó 95 de 130 fallas sintéticas, omitió 35 y generó 118 falsas alarmas. El intervalo Wilson de 95% del recall es [64.9%, 80.0%]. No constituye una estimación de desempeño en tiendas reales.

La validación rechazó datos corruptos. Las 15 pruebas automáticas pasan y una mutación deliberada hizo fallar la prueba esperada. La API local respondió 200 para entradas válidas y 422 para inválidas. Una puerta forzada a 1,01 rechazó el candidato y conservó intacto el modelo vigente. El monitor detectó la perturbación sintética de temperatura.

Decisión recomendada a la junta

Autorizar únicamente la preparación de datos y un piloto en modo sombra: el modelo registra sugerencias mientras continúa el mantenimiento habitual. Medir alertas, capacidad de inspección y resultados a 30 días antes de decidir uso operativo. No prometer reducción de fallas ni ahorro con este experimento.

<b>Pendientes explícitos:</b> GitHub Actions verde/rojo y ejecución Docker, aplazados hasta disponer de GitHub y un entorno con contenedores. Las dos mediciones Kanban pertenecen al trabajo local asistido, no a un equipo humano. El equipo debe completar esas evidencias y validar las metas antes de entregar.

4. Proceso MLOps y métricas

4.1 Datos, definición y validación

Una fila representa un equipo sintético en un corte, con una etiqueta de falla en los siguientes 30 días. Se generaron 2.400 filas con semilla 20261019. El objetivo es Bernoulli con probabilidad logística dependiente de cuatro entradas y ruido independiente. No se ajustó la prevalencia reasignando etiquetas.

El predictor lineal usa 0,50 × uso estandarizado + 0,60 × temperatura estandarizada + 0,50 × días sin mantenimiento estandarizados + 0,35 × incidentes estandarizados + ruido normal de desviación 0,80. El intercepto se calibró a probabilidad media de 0,28. Los parámetros son supuestos didácticos, no relaciones físicas estimadas.

Los rangos son de plausibilidad del ejercicio. La temperatura requiere definir tipo de equipo, sensor y ventana de promedio. Las entradas se generaron independientemente, de modo que no se imponen relaciones causales entre mantenimiento e incidentes. Esta simplificación restringe la validez externa.

4.2 Separación de datos y control de fuga

Partición estratificada persistida: 1.440 entrenamiento, 480 validación y 480 prueba. El escalado se ajusta dentro de Pipeline solo con entrenamiento [3]. Validación elige modelo y puerta; prueba se consulta una vez al final. En datos reales se exige separar por tiempo y equipo, y esperar 30 días para cerrar las etiquetas.

4. Proceso MLOps y métricas (continuación)

4.3 Experimentos y decisión de selección

La puerta de recall 0,50 se fijó después del modelo base (0,2403 en validación), como exige la guía, y antes de comparar variantes. Es deliberadamente baja para demostrar rechazo y aprobación con datos sintéticos [1]. Umbral de clasificación 0,50 y recall mínimo 0,50 son parámetros distintos.

4.4 Resultado final e incertidumbre

Test reservado: exactitud 0.681, precisión 0.446, recall 0.731, F1 0.554, AP 0.525 y ROC-AUC 0.748. Matriz: VP=95, FN=35, FP=118, VN=232. Alertas: 213/480 (44.4%).

Recall = VP/(VP+FN). IC95% Wilson [0.649, 0.800] [5]. Es incertidumbre binomial condicional al modelo y a este generador, no cubre cambio de dominio. La exactitud de predecir siempre ausencia de falla sería 0.729, con recall cero. AP se compara con prevalencia 0.271.

Análisis económico propuesto: pérdida = costo_FN × FN + costo_FP × FP, más operación e intervenciones. No se calcula ahorro sin costos y eficacia preventiva reales. El piloto deberá ajustar el umbral con validación y capacidad de mantenimiento, sin optimizar sobre el test final.

4. Proceso MLOps y métricas (cierre)

4.5 Puerta, servicio, pruebas y automatización

Los candidatos que incumplen recall terminan con código 1 sin generar su archivo. La prueba con umbral imposible 1,01 confirmó rechazo y conservación byte a byte del campeón. La promoción escribe un archivo temporal y lo reemplaza atómicamente. La API carga una vez el mismo Pipeline, valida entradas y devuelve puntaje, clase, versión y advertencia de uso sintético.

Pasaron 15 pruebas: salud, formato y rango de respuesta, rechazo de entradas y paridad con el Pipeline, además de reglas de datos. Se relajó temporalmente el máximo de carga de 100 a 110; una prueba falló y luego se restauró el código. La prueba HTTP real registró 200/200/422 en salud, predicción válida e inválida [6].

Dockerfile y GitHub Actions están preparados, sin ejecuciones acreditadas. El flujo descarga código, instala versiones fijadas, reconstruye el campeón, ejecuta pruebas y construye/consulta el contenedor. El rechazo de entrenamiento detiene pasos posteriores [7]. Python 3.12 se mantiene en local, CI y Docker; la guía admite 3.11 o superior. Compatibilidad Linux pendiente de CI.

4.6 Monitoreo y reentrenamiento

Se generó un lote independiente de 800 casos con semilla 20261020 y otro idéntico salvo +12 °C en temperatura. Se compararon con las 1.440 filas de entrenamiento, sin etiquetas. KS bilateral evalúa cambios marginales. Se corrigieron siete comparaciones con Holm, α familiar=0,01, y se añadió tamaño mínimo D≥0,10 [8,9].

Resultado: alerta solo en temperatura_promedio, D=0.464, p ajustado=9.12e-100. El lote control no generó alertas. El monitor termina con código 1 ante deriva. En variables discretas o redondeadas, el p de KS tiene limitaciones por empates; se trata como diagnóstico y debe complementarse con pruebas de permutación en validación operativa.

Una alerta pide investigar sensores o población, no demuestra que el recall cayó. Reentrenar tras: (1) deriva sostenida en dos lotes semanales de ≥200 equipos; (2) recall <0,50 en dos cohortes maduras con ≥50 fallas cada una; (3) revisión a los 90 días. Cada candidato repite la puerta. Si falla, no sustituye al vigente. Si el vigente también es inadecuado, suspender apoyo predictivo y usar el procedimiento habitual.

Se preservan datos, particiones y commits. MODEL_CARD documenta el alcance, desempeño y límites. En producción harán falta autenticación, control de acceso, auditoría, disponibilidad y validación por tipo de equipo; el prototipo local no acredita esos controles.

No hay datos personales en el dataset. En el piloto real, órdenes de trabajo pueden identificar empleados: minimizar atributos, limitar accesos y separar indicadores de activos de evaluaciones personales. No se incluyen inferencias sobre desempeño individual.

La estrategia define continuidad operativa; Kanban limita capacidad comprometida; ADKAR atiende confianza y práctica; MLOps impide promover candidatos fuera del criterio y vigila cambios. Una buena métrica técnica no basta si no existe personal para inspeccionar las alertas.

No se concluye causalidad: los datos fueron generados con relaciones elegidas por diseño. Un valor alto de una métrica solo acredita que el algoritmo recupera parte de esa señal. No permite afirmar que la antigüedad o el mantenimiento causan fallas ni estimar vida útil.

7. Conclusiones

El prototipo ejecuta validación, experimentación registrada, selección, puerta de calidad, API local, pruebas adversas y monitoreo. La exactitud del modelo base ocultaba baja detección de fallas. La comparación permitió explicitar el intercambio entre recall y carga de inspección.

Las siete etapas se vinculan así: DEFINICION fija la pregunta; datos y esquema evitan entradas corruptas; entrenar y MLflow conservan experimentos; la puerta controla promoción; modelo y Dockerfile describen empaquetado; app expone inferencia; monitoreo y REENTRENAMIENTO vigilan continuidad. Sin cada pieza habría, respectivamente, objetivo ambiguo, datos inválidos, resultados sin trazabilidad, promoción defectuosa, entorno inconsistente, modelo inutilizable o degradación inadvertida.

Docker y CI no están ejecutados. Tampoco se ha probado adopción, impacto económico ni desempeño con equipos reales. La siguiente decisión es cerrar esas evidencias, realizar dos ciclos del equipo y diseñar un piloto en sombra con datos comparables. Si el volumen de falsas alarmas excede la capacidad, revisar el umbral con datos de validación y costos reales.

<b>Declaración de IA:</b> OpenAI Codex apoyó interpretación, diseño, programación, pruebas y redacción. Los resultados técnicos proceden de ejecuciones locales. El equipo debe revisarlos y sustentarlos. No se inventaron entrevistas, aprobaciones, capturas de GitHub ni beneficios empresariales.
